# Voice Conversations with Claude

One of the most distinctive features of Helyx: you can have a **full voice conversation with Claude** directly in Telegram — send a voice message, get a voice reply back.

---

## How it works

### Sending voice to Claude

Record a voice message in Telegram and send it to your session topic. The bot:

1. Transcribes it using **Groq Whisper** (~200ms, free) or local Whisper fallback
2. Forwards the text to Claude CLI as your message
3. Shows a "recording voice..." indicator while Claude's reply is being synthesized

No typing needed. Just talk.

### Getting voice replies

The full reply always lands in Telegram as text — code fences, tables and links intact. Voice is never a rendering of that text; it is a **separate spoken recap**, generated by a small aux LLM and sent alongside the reply in two cases:

| Condition | Behavior |
|---|---|
| You sent a voice message | Claude **always** attaches a recap, regardless of reply length |
| The reply carries ≥200 characters of prose | A recap is generated automatically |

The 200-character threshold is measured on *prose only* — fenced code blocks, inline code, table rows and bare URLs are stripped out before counting, so a reply that's mostly a diff with one sentence of explanation gets no recap: there is nothing worth reading aloud, and asking the model to narrate it produces filler.

This means: if you're having a conversation via voice, Claude always speaks back, however short the reply. If you send a text message, a short or code-heavy reply stays text-only; longer explanations get a spoken recap too.

The recap path above is the one a session takes, through the `reply` tool. Replies the bot itself produces — a `/command` answered in-process, or a reply through the HTTP MCP server — take an older and simpler route (`shouldSendVoice` in `utils/tts.ts`): at least 300 characters of *raw* text, fenced code under 40% of that length, and fewer than 6 diff lines. No recap is generated there; the reply text is synthesized as written. The two thresholds are not a mistake — 300 raw characters and 200 characters of prose are close in practice once code and tables are removed from the count.

### The recap, not the reply, is what gets voiced

An aux LLM call (Groq, `qwen/qwen3.6-27b`) reads the full reply and writes a two-to-eight-sentence recap in plain prose — no markdown, no code, no file paths or identifiers, described in words instead ("the provider service", not `provider-service.ts`). The recap is posted as its own message, rendered as a collapsed Telegram blockquote (🔊 prefix, "show more" to expand), and *that* text — not the original reply — is what gets synthesized to voice.

Sending the recap as its own collapsed message rather than folding it into the reply is deliberate: the operator has already read the reply once, and an expandable quote costs nothing to scroll past however long it is.

### LLM normalization before speech

Each spoken chunk also goes through a second, separate aux LLM pass (same Groq model, `qwen/qwen3.6-27b`, `reasoning_effort: none`, ~150ms) that rewrites it to sound natural when spoken:

- `channel/session.ts` → "session dot ts"
- `lease_expires_at` → "lease expires at"
- `acquireLease()` → "acquire lease"
- Git hashes → omitted or "the commit"
- URLs → omitted or "at the link"
- Same language as input (Russian stays Russian) — an earlier model (`llama-3.1-8b-instant`) sometimes translated instead of transliterating, e.g. turning `--build bot` into `--строить бот`

### Long recaps: multiple voice tracks

A recap can run long. The text of the recap is never cut for this — it is sent whole, in one collapsed quote. Only the *audio* is divided: it's split into tracks of roughly 90 spoken seconds each (about 1,350 characters at the default speaking-rate estimate, tunable via `VOICE_CHARS_PER_SECOND`), split on paragraph, then sentence, then word boundaries so a track never cuts mid-word. A long recap arrives as one block of text and several voice messages, sent in order.

## Voice providers

### Transcription (speech → text)

| Provider | Config | Notes |
|---|---|---|
| **Groq Whisper** | `GROQ_API_KEY` | Primary; ~200ms, free tier at [console.groq.com](https://console.groq.com) |
| **Local Whisper** | auto-detected | Fallback; slower, runs on device |

### Synthesis (text → speech)

`TTS_PROVIDER` selects the engine: `auto` (the default), or one of `piper`,
`yandex`, `kokoro`, `openai`, `groq` to pin a single one — or `none` to turn
synthesis off entirely.

On `auto` the chain is picked by the language of the text, and it starts
locally:

| Text | Chain |
|---|---|
| Russian | **Piper** (local, `PIPER_MODEL_RU`) → Yandex SpeechKit → Groq Orpheus |
| English | **Piper** (local, `PIPER_MODEL_EN`) → Kokoro (local) → Groq Orpheus |

| Provider | Config | Notes |
|---|---|---|
| **Piper** | `PIPER_DIR`, `PIPER_MODEL_RU` / `PIPER_MODEL_EN` | First in `auto`; runs on device, no API key, no per-reply cost |
| **Yandex SpeechKit** | `YANDEX_API_KEY` + `YANDEX_FOLDER_ID` | Best Russian quality and the best at mixed Russian/English; second by choice, not by measurement — whoever is first is paid for on every spoken reply |
| **Kokoro** | `KOKORO_VOICE`, `KOKORO_DTYPE` | Local English fallback when Piper is unavailable; model bundled via `kokoro-js`, no API key. Voice defaults to `af_bella`, quantization to `q8` |
| **Groq Orpheus** | `GROQ_API_KEY` | Last resort for both languages; English-only voice; free tier |
| **OpenAI TTS** | `OPENAI_API_KEY` | Only when pinned with `TTS_PROVIDER=openai` |

Yandex SpeechKit requires a service account with `ai.speechkit.tts` IAM role. See [Yandex Cloud docs](https://cloud.yandex.ru/docs/speechkit/) for setup.

## Setup

Add to your `.env`:

```env
# Transcription + TTS normalization (free)
GROQ_API_KEY=gsk_...

# Voice synthesis — Russian-first (best quality)
YANDEX_API_KEY=AQVN...
YANDEX_FOLDER_ID=b1g...
```

Both keys are optional — the bot degrades gracefully:
- No `GROQ_API_KEY` → transcription falls back to local Whisper; the recap and the speech-normalization passes are skipped
- No Yandex keys → Piper still speaks; Russian just loses its paid fallback
- Nothing configured at all → Piper and Kokoro are local, so voice keeps working; `TTS_PROVIDER=none` is what actually turns it off

## Example flow

```
You:    🎤 "Explain what the resolveSession function does"
                    ↓ Groq Whisper (~200ms)
Claude: [thinking... reading files...]
Claude: 📝 "resolveSession is responsible for..." (long explanation)
Claude: 🔊 "The function resolves which session a message belongs to..." (collapsed recap)
Claude: 🎤 [one or more voice messages of the recap, synthesized via Piper]
```

The recap and its voice arrive right after the text reply, generated in parallel with nothing held up waiting for them.

## Troubleshooting

**Voice sent but no voice reply:**
- The reply may carry under 200 characters of prose once code, tables and URLs are stripped — this is by design, there is nothing to say aloud
- `TTS_PROVIDER=none` disables synthesis outright
- Piper missing or its voice model absent (`PIPER_DIR`, `PIPER_MODEL_RU` / `PIPER_MODEL_EN`) — the log line `tts: Piper failed` says so, and the chain moves on
- Check `YANDEX_API_KEY` / `YANDEX_FOLDER_ID` — Yandex errors appear in bot logs
- No `GROQ_API_KEY` → no recap is generated at all, so nothing gets spoken on the session path
- Groq Orpheus has a 3600 token/day free limit; check if exhausted

**Transcription fails / wrong language:**
- Whisper auto-detects language; works best with clear audio
- For Russian, Groq Whisper handles it well natively

**Voice reply is in wrong Telegram topic:**
- This was a bug fixed in `channel/tools.ts` (April 2026) — update to latest
